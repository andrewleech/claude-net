# P1 findings: async-TLS de-risking

Date: 2026-07-23
Anchors: claude-net `main` @ `4f564a56b9`, picolet `dev` @ `2fe3ef5d14`

This note distils the P1 spike that de-risks running a `wss` connection's TLS
handshake and post-handshake I/O entirely under one non-blocking asyncio poll
loop on the picolet cli+TLS binary. Artifacts live in `planning/spike/`.

## Outcome

PASS-with-residuals — top risk retired, no C change required, minor
Python-side and coverage residuals to clear before P3.

## Which async-TLS path works

Path (a), `asyncio.open_connection(host, port, ssl=ctx,
server_hostname=...)`, works and is what the deliverables use. No hand-rolled
poll driver (path b) was needed or written.

On this binary `extmod/asyncio/stream.py` wraps the already-non-blocking
socket with `do_handshake_on_connect=False`; the mbedtls handshake surfaces
`WANT_READ`/`WANT_WRITE` as `EAGAIN`, and the poll loop drives it to
completion on first read/write. The full sequence — TLS handshake, WebSocket
upgrade, post-handshake framed I/O, and concurrent stdin — all run under one
`select.poll` loop. The handshake is genuinely poll-blocked, not busy-spun: a
3 s mid-handshake ServerHello stall consumed ~0.08–0.1 s CPU (~3 %), and a
concurrent asyncio ticker was observed firing ~30 times across a stalled 1.5 s
handshake, confirming the event loop is not blocked in C.

Module details confirmed: the TLS module is `tls` (not `ssl`); mbedtls
backend; bundled CA must be DER (PEM parsing off); SNI is mandatory.
Negotiated TLS was 1.2 (mbedtls/server default).

## Buffered-record semantics

Verdict: handled at the C level — NO Python drain-after-read loop is required.

`extmod/modtls_mbedtls.c` `socket_ioctl(MP_STREAM_POLL)` consults
`mbedtls_ssl_check_pending()` and reports `MP_STREAM_POLL_RD` when mbedtls
holds decrypted-but-unconsumed application data with nothing left on the raw
fd. asyncio's `IOQueue` poll therefore wakes the reader for a second WebSocket
frame packed into the same TLS record, with zero new fd activity.

Proof: the mock server's `pack` mode writes two complete WS frames in one TLS
record then goes genuinely silent (no liveness pinger in `pack` mode). Frame 1
is returned on the first read, which drains the whole record off the fd into
mbedtls's internal buffer; frame 2 was then delivered in 2–3 ms. With no fd
activity to wake poll, that latency can only originate from `check_pending`; a
broken path would hang to the reader's `wait_for` timeout.

Caveat on the mechanism proof: `SSLSocket` does not expose `ioctl()` to Python
on this build (a direct probe raises `AttributeError`), so the C path is
reachable only through the stream protocol that `select.poll` uses internally —
exactly the path asyncio drives. The timed silent-server behavioural test is
therefore the authority; keep it in the permanent suite as the sole guard,
since the guarantee could regress silently if the mbedtls config changes.

## Measurements

| Metric | Value |
|---|---|
| Handshake+upgrade, local server | ~60–95 ms |
| Handshake+upgrade, real hub (CERT_NONE) | 117–215 ms across runs (145 ms typical) |
| Handshake+upgrade, real hub (CERT_REQUIRED) | 141–208 ms across runs (177 ms typical) |
| Idle-connected RSS, local | ~3.0–3.1 MB (3084–3112 KB) |
| Idle-connected RSS, real hub | ~3.3–3.4 MB |
| Idle CPU, 3 s handshake stall | ~0.08–0.1 s CPU / 3.0 s wall (~3 %) |
| Idle CPU, live connection hold | ~2.7–3.3 % over the window |
| Buffered frame-2 latency (silent server) | 2–3 ms |

RSS is comfortably under the 4 MB budget in every mode. The nonzero idle CPU
is the reader's `wait_for` timeout wakeup granularity plus per-PING TLS work,
not busy-spin.

## Real-hub status

Proven, not documented-unreachable. `wss://telie.story-kettle.ts.net:4815/ws`
resolved to tailnet `100.82.58.55` and connected from the sandbox. Both cert
modes registered successfully:

- CERT_NONE: register (two-frame reply) + ping (two frames), rc=0.
- CERT_REQUIRED with `isrg_root_x1.der`: validated the hub's real Let's
  Encrypt chain against ISRG Root X1 (SNI passed), register + ping, rc=0.

A ~12 s live hold survived without eviction, auto-PONGing the hub's ~5 s WS
control PINGs under the async loop.

## Residuals to clear before P3

- The stall/EAGAIN regression test (test 2) asserts only completion strings
  and rc, not CPU or concurrent-task liveness during the stall. A future
  busy-spin or block-in-C regression would still pass it. Add a CPU sample or
  a concurrent-ticker assertion across the stall window. Current behaviour was
  confirmed correct out-of-band; this is a weak-guard gap, not a live defect.
- `WSClient.connect` (`ws.py`) leaks the writer/socket on the 101-upgrade
  failure path and on exceptions during the handshake-driving exchange.
  Harmless in one-shot spike scripts; a real fd leak for the persistent,
  reconnecting production plugin. Wrap the post-open exchange in try/except
  that closes the writer before re-raising.
- `WSClient.recv` has an unguarded fragmentation edge: a leading `OP_CONT`
  frame with `fin=1` reaches `return bytes(frags)` with `frags=None`
  (TypeError). Not triggered by the hub; a malformed/hostile peer would crash
  the reader. Guard the return with `if frags is not None`.
- Real-hub liveness confirmed only over a ~12 s hold; hub eviction is ~30 s.
  Run a >30 s soak in P3 to confirm sustained PONG keepalive.
- The `pack` proof used one TLS record (~162–172 bytes). A large payload
  spanning multiple TLS records under the `MICROPY_PY_SSL` fragment limit was
  not exercised; add a multi-record buffered-read test in P3.
- Negotiated TLS was 1.2. If the real hub or P3 requires TLS 1.3, retest the
  buffered-record path under 1.3 (new-session-ticket handling differs).
- Idle CPU is a function of the reader's periodic `wait_for` timeout; the
  production port should prefer a plain `await recv()` (no periodic timeout)
  driven off a shutdown Event to reach true zero-wakeup idle.
- `realhub_hold.py` proves register + WS-control-PING/PONG liveness but never
  sends an application-level `{action:'ping'}` to the real hub (only the local
  mock is driven with the ping action). Add one app-ping round-trip so the
  real-hub proof matches the local test shape.

Fixed during the spike (not carried forward): `WSClient.recv` EOF contract —
an abrupt mid-frame close previously raised an uncaught `EOFError`, making the
documented `None`-on-close return dead code. `_read_frame` now catches both
`EOFError` (clean FIN) and `OSError`/`ECONNRESET` (genuine RST, the real-hub
eviction shape) and returns `None`; verified against both shapes over TLS
(test 8).

## Escalation

Not triggered. No MicroPython C source was edited and no runtime was rebuilt.
The two C behaviours P1 depends on already work on this binary: (1) the
mbedtls handshake surfaces `WANT_READ`/`WANT_WRITE` as `EAGAIN` and
`asyncio.open_connection` drives it under the poll loop without blocking the
loop, and (2) `modtls_mbedtls.c` `socket_ioctl(MP_STREAM_POLL)` reports
readability from `mbedtls_ssl_check_pending()` so buffered decrypted data
surfaces with no fd activity. All residuals are Python-side hygiene / coverage
items requiring no C change or decision from Andrew.
